# Release history

> For: anyone choosing or reviewing a Workflow release. Last checked with: Workflow 2.11.0.

One line per release, newest first. Every release is immutable: a wrong one is
replaced by a new version, never edited. Each notes link is the release page,
which lists the package and its checksums. Check the
[Workflow Controller compatibility page](https://github.com/RodrigoFAbreu/workflow-controller/blob/main/docs/compatibility.md)
before updating a repository the Controller drives.

| Release | Date | What changed | Notes |
|---|---|---|---|
| 2.11.0 | 2026-10-13 | A plan revision's checkpoint anchors are now checked before any plan review: when the revision is published (`/milestone-plan`, `/request-plan-amendment`), when it is bound (`/apply-plan-review`) and when its plan-review bundle is generated, each refuses a plan without anchors with one next step, instead of the first refusal coming at plan approval after both plan reviews. The command texts write anchors from revision 1. Workflow 2.11.0 writes nothing new: no state field, value, record, configuration key or commit shape, so 2.10.0 reads everything 2.11.0 writes and can drive a repository on 2.11.0. Moving back to 2.10.0 loses only the early refusals: an amending plan without anchors is again refused first at plan approval, after both plan reviews, and a new plan without anchors is accepted, so its first amendment demotes every completed checkpoint. Plans already written with anchors keep them, and 2.10.0's reconciliation uses them. This repository's own installed copy of the workflow changes only when it updates to 2.11.0. Orchestration Protocol 1.3 (unchanged). | [2.11.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.11.0) |
| 2.10.0 | 2026-10-11 | New work items stop starting on "2.1": while the configuration names "2.1" as the default, creating a new work item (a fresh `/milestone-plan`, or a broad remediation child from `/apply-functional-review` or `/apply-pr-review`) refuses before any write with `DefaultWorkflowVersionRetiredError` and one next step, setting the default to "2.2" in a `Workflow-Activation: 2.2` commit. Existing "2.1" items run to completion, legacy adoption still targets "2.1", "2.1" stays supported, and nothing persisted changes. Orchestration Protocol 1.3 adds row 1b (`blocked`, `plan_start_default_retired`) and an advisory `verify` check, `default_workflow_version`. The managed `workflow-conformance.yml` cancels a pull request's superseded run on a new push (push runs are never cancelled) and runs its nine suites in parallel inside the one job, each isolated. Two version-aware wording fixes. 2.10.0 writes no new state, field or value, so 2.9.2 reads everything 2.10.0 writes; on a move back to 2.9.2 the refusal and row 1b disappear and the advisory check is not run. This repository's own installed copy of the workflow changes only when it updates to 2.10.0. Orchestration Protocol 1.3. | [2.10.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.10.0) |
| 2.9.2 | 2026-10-10 | A fix so a bounded functional-review fix no longer needs a person: `/apply-functional-review` now commits the stale technical-approval write, the fix and the functional-review checklist first and the bundle-generation record last, so the next implementation review no longer stops with `bundle_generation_mismatch`. The trailer rule is stated plainly in every command: `Co-Authored-By:` and `Claude-Session:` lines go in their own paragraph before the `Workflow-*` trailers, and a refused generation record names that cause. Read-side checks stay strict. 2.9.2 accepts no commit shape that 2.9.1 refuses and writes none that 2.9.1 would refuse, so 2.9.1 reads everything 2.9.2 writes; on a move back to 2.9.1, whose command keeps the old order, commit the stale technical-approval write alone before the first fix edit, commit the checklist before the generation record, and keep `Co-Authored-By:` out of the trailer paragraph, all by hand. Orchestration Protocol unchanged at 1.2. | [2.9.2](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.9.2) |
| 2.9.1 | 2026-10-09 | A fix for the dead end after an implementation review returns REVISE: the review now commits its own REVISE write, `/apply-implementation-review` commits a still-pending one, and also commits its own entry into the applying-feedback phase, for every governing version, and the rule that an APPROVE write is never committed on its own is written down. 2.9.1 accepts no commit shape that 2.9.0 refuses and writes none that 2.9.0 would refuse, so 2.9.0 reads everything 2.9.1 writes; on a move back to 2.9.0, whose commands do not commit these writes, commit the state file alone by hand, before the first fix commit. Orchestration Protocol unchanged at 1.2. | [2.9.1](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.9.1) |
| 2.9.0 | 2026-10-08 | New installations default to governing version 2.2. The user-only `/retire-legacy-work-item` closes a finished legacy work item for good, and `/resume-implementation` returns an item to implementation. A version-1 item can now enter implementation review. Orchestration Protocol 1.2. | [2.9.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.9.0) |
| 2.8.0 | 2026-10-03 | A gate policy: approval gates are automatic by default (all three only for version-2.2 items), and a person can be turned on for all of them or one. A red or changes-requested pull request reopens the same work item. Orchestration Protocol 1.1. | [2.8.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.8.0) |
| 2.7.0 | 2026-10-02 | The Orchestration Protocol, so a tool can drive the Workflow, and a fix so withdrawn plan content can never be reviewed again. | [2.7.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.7.0) |
| 2.6.0 | 2026-09-30 | Safer reviews and parallel work: per-item feedback folders, hardened plan-review binding and cross-worktree coordination. | [2.6.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.6.0) |
| 2.5.1 | 2026-09-30 | A fix to checkpoint ids ending in a letter so a plan amendment can use them. | [2.5.1](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.5.1) |
| 2.5.0 | 2026-09-30 | Implementation review in two stages, local then external, like plan review. | [2.5.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.5.0) |
| 2.4.0 | 2026-09-30 | Changing an approved plan during implementation (`/request-plan-amendment`). | [2.4.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.4.0) |
| 2.3.1 | 2026-09-30 | The first published release, the original Workflow baseline. | [2.3.1](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.3.1) |
