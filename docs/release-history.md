# Release history

> For: anyone choosing or reviewing a Workflow release. Last checked with: Workflow 2.13.0.

One line per release, newest first. Every release is immutable: a wrong one is
replaced by a new version, never edited. Each notes link is the release page,
which lists the package and its checksums. Check the
[Workflow Controller compatibility page](https://github.com/RodrigoFAbreu/workflow-controller/blob/main/docs/compatibility.md)
before updating a repository the Controller drives.

| Release | Date | What changed | Notes |
|---|---|---|---|
| 2.13.0 | 2026-10-17 | Three review-loop defects fixed. The changes file, `CHANGES_SINCE_REVIEW.md`, now holds one section per review stage: the local section compares against the previous bundle generation as before, and the manual external section compares against the content that stage last reviewed and quotes that stage's own last verdict, so an external reviewer's later round sees the changes since its own last verdict, not the last local round's (plan and implementation stages; the file and the baselines stay outside `bundle_id` and `review_content_id`). The baseline is written at the manual ingest, under the state lock, into the gitignored `.ai-review/<id>/review-baselines/`; any failure falls to an explicit full review, which also is the first manual round after the update. A frozen real-process test no longer reads a half-written ready file (the ready file is published atomically). The governing-version sweep now runs when a plan revision is published, bound or turned into a plan-review bundle, as 2.11.0 does for checkpoint anchors, so a plan the installed conformance sweep would reject is refused before any review, with one next step; approved and bound plans keep working until their next revision. The release carries a `manager` metadata block in `manifest.json` (authored: minimum Manager `1.13.0`, empty downgrade posture, one `new_work_only` entry, no gate default change, no portability exceptions; computed: the per-suite test counts, measured from the staged conformance fixture), and CI checks it against the contract, against committed publication evidence for the Manager releases, and with an update fixture built from the v2.12.0 bootstrap and the released minimum Manager. Closes workflow#35 and #32, and #30 part 1 (part 2 stays open). Workflow 2.13.0 writes no new key or value to `WORKFLOW_STATE.json` or `WORKFLOW_CONFIG.json`, no new commit shape and no new phase. It adds one gitignored directory, `.ai-review/<id>/review-baselines/`, and changes the layout of the gitignored `CHANGES_SINCE_REVIEW.md`. After a move back to 2.12.0 the early sweep refusal is gone (a plan the installed sweep rejects reaches review again); the directory is ignored and not deleted: delete `.ai-review/<id>/review-baselines/` on downgrading (as 2.12.0's paragraph says to delete `CHANGES_SINCE_REVIEW.md`), so the first manual round after a re-upgrade is a full review; and a 2.13.0-shaped changes file still opens with the `review_content_id:` line a 2.12.0 reviewer checks, but its first section is the local one only by convention (2.12.0 regenerates the file in its own shape at the next generation). Nothing is lost from state, so the manifest block's downgrade posture is empty. This repository's own installed copy of the workflow changes only when it updates to 2.13.0. Orchestration Protocol 1.4 (unchanged). | [2.13.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.13.0) |
| 2.12.0 | 2026-10-15 | Review rounds converge. From round 2 a plan or implementation review (local and external stage) is given the changes since the last reviewed bundle and that round's findings, in a gitignored `CHANGES_SINCE_REVIEW.md` beside the bundle and in the archive; an approval still binds the full content. A verdict is checked for shape before it becomes state: a `REVISE` must name a Blocking or Important finding, an `APPROVE` may not list a Blocking finding or declare `Review scope: changes`, and a malformed verdict is refused and reissued, never converted. Orchestration Protocol 1.4 adds the `review_round` field to the `next-action` snapshot (derived from existing state; accepting at a cap stays a person's step) and states when a distinct-provider verdict courier at an `external_gate` is admissible (documentation only). `/milestone-plan` and `/apply-plan-review` ask for small plans and warn, without blocking, above 6 checkpoints. Closes workflow#28. Workflow 2.12.0 writes no new key or value to `WORKFLOW_STATE.json` or `WORKFLOW_CONFIG.json` and no new commit shape. It adds one gitignored file, `.ai-review/<id>/CHANGES_SINCE_REVIEW.md`, outside `bundle_id` and `review_content_id`, and one optional verdict header line, `Review scope:`. Workflow 2.11.0 never reads either: after a move back it ignores the header line, does not regenerate or delete the file (delete it by hand so a reviewer does not read a stale copy), and verifies an archive that carries it. A move back loses the severity refusal and the `review_round` field (an orchestrator reading protocol 1.4 sees 1.3 again). `review_round.plan` is exact only for an item whose plan-review rounds all ran under 2.7.0 or later; a consumer that must enforce a hard cap on any other repository counts rounds itself. This repository's own installed copy of the workflow changes only when it updates to 2.12.0. Orchestration Protocol 1.4. | [2.12.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.12.0) |
| 2.11.0 | 2026-10-13 | A plan revision's checkpoint anchors are now checked before any plan review: when the revision is published and when it is bound (`/milestone-plan`, `/apply-plan-review`), and when its plan-review bundle is generated, each refuses a plan without anchors with one next step, instead of the first refusal coming at plan approval after both plan reviews. The command texts write anchors from revision 1. Workflow 2.11.0 writes nothing new: no state field, value, record, configuration key or commit shape, so 2.10.0 reads everything 2.11.0 writes and can drive a repository on 2.11.0. Moving back to 2.10.0 loses only the early refusals: an amending plan without anchors is again refused first at plan approval, after both plan reviews, and a new plan without anchors is accepted, so its first amendment demotes every completed checkpoint. Plans already written with anchors keep them, and 2.10.0's reconciliation uses them. This repository's own installed copy of the workflow changes only when it updates to 2.11.0. Orchestration Protocol 1.3 (unchanged). | [2.11.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.11.0) |
| 2.10.0 | 2026-10-11 | New work items stop starting on "2.1": while the configuration names "2.1" as the default, creating a new work item (a fresh `/milestone-plan`, or a broad remediation child from `/apply-functional-review` or `/apply-pr-review`) refuses before any write with `DefaultWorkflowVersionRetiredError` and one next step, setting the default to "2.2" in a `Workflow-Activation: 2.2` commit. Existing "2.1" items run to completion, legacy adoption still targets "2.1", "2.1" stays supported, and nothing persisted changes. Orchestration Protocol 1.3 adds row 1b (`blocked`, `plan_start_default_retired`) and an advisory `verify` check, `default_workflow_version`. The managed `workflow-conformance.yml` cancels a pull request's superseded run on a new push (push runs are never cancelled) and runs its nine suites in parallel inside the one job, each isolated. Two version-aware wording fixes. 2.10.0 writes no new state, field or value, so 2.9.2 reads everything 2.10.0 writes; on a move back to 2.9.2 the refusal and row 1b disappear and the advisory check is not run. This repository's own installed copy of the workflow changes only when it updates to 2.10.0. Orchestration Protocol 1.3. | [2.10.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.10.0) |
| 2.9.2 | 2026-10-10 | A fix so a bounded functional-review fix no longer needs a person: `/apply-functional-review` now commits the stale technical-approval write, the fix and the functional-review checklist first and the bundle-generation record last, so the next implementation review no longer stops with `bundle_generation_mismatch`. The trailer rule is stated plainly in every command: `Co-Authored-By:` and `Claude-Session:` lines go in their own paragraph before the `Workflow-*` trailers, and a refused generation record names that cause. Read-side checks stay strict. 2.9.2 accepts no commit shape that 2.9.1 refuses and writes none that 2.9.1 would refuse, so 2.9.1 reads everything 2.9.2 writes; on a move back to 2.9.1, whose command keeps the old order, commit the stale technical-approval write alone before the first fix edit, commit the checklist before the generation record, and keep `Co-Authored-By:` out of the trailer paragraph, all by hand. Orchestration Protocol unchanged at 1.2. | [2.9.2](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.9.2) |
| 2.9.1 | 2026-10-09 | A fix for the dead end after an implementation review returns REVISE: the review now commits its own REVISE write, `/apply-implementation-review` commits a still-pending one, and also commits its own entry into the applying-feedback phase, for every governing version, and the rule that an APPROVE write is never committed on its own is written down. 2.9.1 accepts no commit shape that 2.9.0 refuses and writes none that 2.9.0 would refuse, so 2.9.0 reads everything 2.9.1 writes; on a move back to 2.9.0, whose commands do not commit these writes, commit the state file alone by hand, before the first fix commit. Orchestration Protocol unchanged at 1.2. | [2.9.1](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.9.1) |

A version-1 item can now enter implementation review. Orchestration Protocol 1.2. | [2.9.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.9.0) |
