# Release history

> For: anyone choosing or reviewing a Workflow release. Last checked with: Workflow 2.17.0.

One line per release, newest first. Every release is immutable: a wrong one is
replaced by a new version, never edited. Each notes link is the release page,
which lists the package and its checksums. Check the
[Workflow Controller compatibility page](https://github.com/RodrigoFAbreu/workflow-controller/blob/main/docs/compatibility.md)
before updating a repository the Controller drives.

| 2.17.0 | 2026-10-19 | The backlog file. A repository can declare a structured backlog file (a strict YAML subset) and an optional roadmap generator in `WORKFLOW_CONFIG.json`; `/milestone-plan` with no argument takes the next ready item from it (a ready `in-progress` item first, otherwise the lowest-ordered ready `next` item whose dependencies are `done`, with the choice and any blocked `in-progress` items reported), and `/accept-milestone` and `/satisfy-gate acceptance` set the item `done` (optionally recording the `release`) and regenerate the roadmap page inside the acceptance commit. `scripts/workflow_backlog.py` (standard library only, not a state writer) ships the parser and schema, the selection, the status edit that re-parses to prove nothing else changed, a deterministic built-in roadmap page or a declared generator under a freshness contract, and the `next`, `accept`, `generate` and `check` command line; `check` runs no user code and fails on a page edited by hand. A malformed or missing declared file fails closed with a code and one next step, never a fall-back to prose. The declared file, roadmap page and `docs/items/` are classified as excluded by the artifact declaration, with a repair for items in flight at adoption, and the new `docs/ai-workflow/BACKLOG_FILE.md` is the consumer reference. A repository that declares nothing behaves exactly as under 2.16.0. No state key, phase, status, commit shape or protocol field changes, and Orchestration Protocol stays 1.5. Moving back to 2.16.0 (`workflow-manager update` to 2.16.0, minimum Manager 1.13.0): 2.16.0 ignores the `backlog` key, so `/milestone-plan` reads the generated page as prose and acceptance hand-edits it, after which the staleness check fails in that repository's CI (with a non-default `roadmap` nothing fails and the backlog silently stops advancing); finish or accept the items in flight first, then either keep the backlog by copying `scripts/workflow_backlog.py` to `tools/workflow_backlog.py` before the update and running its `generate` at each acceptance, or delete the `backlog` key and the CI check. Still open: #30 part 2, #31, #39, #45, #50 and #52. This repository keeps its prose `docs/ROADMAP.md`, and its own installed copy of the workflow changes only when it updates to 2.17.0. Orchestration Protocol 1.5. | [2.17.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.17.0) |
| 2.16.0 | 2026-10-19 | Faster managed conformance. The `workflow-conformance` job that `workflow-manager` installs now runs the acceptance-matrix suite (the longest, 415 tests) in four shards of whole test classes instead of as one unit; the shards and the eight other suites share the one queue and the one width limit of 4, acceptance shards first. A coverage gate compares the test ids the shards recorded with the ids planned and refuses a missing, extra or duplicated id (`coverage: expected 415, recorded 415`), a failing shard shows as `acceptance N/4` with an `::error` annotation naming the shard, its classes and the failing test ids, and every shard log is in the job log (a collapsed group for a passing shard, unfolded after the `::error` annotation for a failing one). Measured on GitHub-hosted runners (45 jobs, timings compared only on the same runner type, outcome O1, evidence in `docs/ai-workflow/CONFORMANCE_SHARDING_EVIDENCE.md`): the median step wall fell from 1212.5 s to 979 s on the AMD EPYC 7763 type (ratio 0.8074) and from 833.5 s to 606 s on the AMD EPYC 9V45 type (ratio 0.7271). This repository's own `release-source-conformance` job uses the same scheduling. The payload changes only its release constant (`WORKFLOW_RELEASE`, with the three matching edits of `ORCHESTRATION_PROTOCOL.md`); no behaviour, state key, phase, configuration key, commit shape or protocol field changes, and Orchestration Protocol stays 1.5. After a move back to 2.15.0 (`workflow-manager update` to 2.15.0) the unsharded conformance job returns and nothing else changes. Still open: #30 part 2, #31, #39, #45, #52, #48 and #50. This repository's own installed copy of the workflow changes only when it updates to 2.16.0. Orchestration Protocol 1.5. | [2.16.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.16.0) |
| 2.15.0 | 2026-10-18 | Review round counts. A work item created under 2.15.0 records, in its state and in each verdict's own transaction, one local or one external round per recorded `APPROVE` or `REVISE` of each review stage (`review_round_counts`), so a cap on review rounds no longer depends on counting by hand. Orchestration Protocol 1.5 adds four fields to the `next-action` snapshot's `review_round`, `plan_local`, `plan_external`, `implementation_local` and `implementation_external` (a number, or `null` when not recorded: an item created before 2.15.0, a promoted legacy item, a feedback-only item or a malformed key); `plan`, `implementation` and `current` are unchanged, and a 1.4 reader ignores the new fields. Closes workflow#43; #30 part 2, #31, #39, #45 and #48 stay open. Workflow 2.15.0 adds one work-item key to `WORKFLOW_STATE.json`, `review_round_counts`; no phase, status, configuration key or commit shape changes. After a move back to 2.14.0 the key stays and the validator and pure writers ignore it, but 2.14.0's commit helpers do not name it, which has two consequences. While the key is an uncommitted change of an item's entry, 2.14.0 rejects the item (for example `ReviewStageWriteNotCommittableError`): let the item's pending state be committed under 2.15.0 first (`git diff HEAD -- docs/ai-workflow/WORKFLOW_STATE.json` shows no `review_round_counts` hunk). And once a commit that changes the key is in a non-terminal item's open implementation-stage provenance interval (for example a provenance recovery that committed a local `APPROVE`'s pending ledger and counter in a recovered generation record), 2.14.0 raises `MalformedBundleGenerationRecordCommitError` at the next provenance check even on a clean tree, and committing the state does not help: finish that item's implementation approval under 2.15.0, or keep the repository on 2.15.0 until it has. The supported boundary is therefore: move back to 2.14.0 only when every item's pending state is committed and no non-terminal item has such a commit. After the move the snapshot loses the four fields and the protocol reads 1.4 again; verdicts ingested while downgraded are not counted, and nothing marks that, so after a re-upgrade the counts read low (a consumer holding a hard cap counts itself). This repository's own installed copy of the workflow changes only when it updates to 2.15.0. Orchestration Protocol 1.5. | [2.15.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.15.0) |
| 2.14.0 | 2026-10-18 | Three gaps closed. (1) Optional review findings are no longer lost in the gitignored archive: every Optional finding of every recorded verdict of a two-stage item (local and manual, plan and implementation, `APPROVE` or `REVISE`) is recorded in the item's state at ingest, in the verdict's own transaction, keyed by its text so a finding raised again is one entry. Acceptance (`/accept-milestone` and `/satisfy-gate acceptance`, under every gate policy) refuses while a recorded finding has no disposition: fixed, dropped with a reason, or a follow-up with a link, in `docs/ai-workflow/registry/<id>-dispositions.json` (`python3 scripts/workflow_state.py --finding-dispositions <id>` lists them and prints a skeleton). A follow-up is a complete disposition, so acceptance never waits for its fix. The dispositions are written into a committed completed-milestone record, `docs/milestones/completed/<id>-findings.md`. (2) `verify`, `/adopt-gate-policy` and `GATE_POLICY.md` name the cause of a gate-policy adoption merged with a merge commit, which leaves older policy files counting on that line, and the fix (merge an adoption with a squash); the evaluation is unchanged. (3) A plan revision whose artifact declaration leaves a path named in a Files paragraph unclassified, at the plan stage or the implementation stage, is refused when published, bound or turned into a plan-review bundle, with one next step; a plan with no Files paragraph gets an advisory. Plans already approved or bound are not re-checked. Closes workflow#34, #37 and #40; #30 part 2, #31 and #39 stay open. Workflow 2.14.0 adds one work-item key to `WORKFLOW_STATE.json`, `optional_findings`, and two committed files for an item that has findings; no phase, status, configuration key or commit shape changes (the commit-field sets admit the key). After a move back to 2.13.0 the key stays and the validator and pure writers ignore it, but 2.13.0's commit helpers reject an item whose `optional_findings` is still an uncommitted change (for example `ReviewStageWriteNotCommittableError`): before moving back, let the item's pending state be committed under 2.14.0 (`git diff HEAD -- docs/ai-workflow/WORKFLOW_STATE.json` shows no `optional_findings` hunk). Acceptance then no longer asks for dispositions, verdicts ingested while downgraded are not recorded (after a re-upgrade triage their Optional findings by hand at acceptance), and the adoption notice and the declaration check are gone. Findings are recorded from the first verdict ingested after the update. This repository's own installed copy of the workflow changes only when it updates to 2.14.0. Orchestration Protocol 1.4 (unchanged). | [2.14.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.14.0) |
| 2.13.0 | 2026-10-17 | Three review-loop defects fixed. The changes file, `CHANGES_SINCE_REVIEW.md`, now holds one section per review stage: the local section compares against the previous bundle generation as before, and the manual external section compares against the content that stage last reviewed and quotes that stage's own last verdict, so an external reviewer's later round sees the changes since its own last verdict, not the last local round's (plan and implementation stages; the file and the baselines stay outside `bundle_id` and `review_content_id`). The baseline is written at the manual ingest, under the state lock, into the gitignored `.ai-review/<id>/review-baselines/`; any failure falls to an explicit full review, which also is the first manual round after the update. A frozen real-process test no longer reads a half-written ready file (the ready file is published atomically). The governing-version sweep now runs when a plan revision is published, bound or turned into a plan-review bundle, as 2.11.0 does for checkpoint anchors, so a plan the installed conformance sweep would reject is refused before any review, with one next step; approved and bound plans keep working until their next revision. The release carries a `manager` metadata block in `manifest.json` (authored: minimum Manager `1.13.0`, empty downgrade posture, one `new_work_only` entry, no gate default change, no portability exceptions; computed: the per-suite test counts, measured from the staged conformance fixture), and CI checks it against the contract, against committed publication evidence for the Manager releases, and with an update fixture built from the v2.12.0 bootstrap and the released minimum Manager. Closes workflow#35 and #32, and #30 part 1 (part 2 stays open). Workflow 2.13.0 writes no new key or value to `WORKFLOW_STATE.json` or `WORKFLOW_CONFIG.json`, no new commit shape and no new phase. It adds one gitignored directory, `.ai-review/<id>/review-baselines/`, and changes the layout of the gitignored `CHANGES_SINCE_REVIEW.md`. After a move back to 2.12.0 the early sweep refusal is gone (a plan the installed sweep rejects reaches review again); the directory is ignored and not deleted: delete `.ai-review/<id>/review-baselines/` on downgrading (as 2.12.0's paragraph says to delete `CHANGES_SINCE_REVIEW.md`), so the first manual round after a re-upgrade is a full review; and a 2.13.0-shaped changes file still opens with the `review_content_id:` line a 2.12.0 reviewer checks, but its first section is the local one only by convention (2.12.0 regenerates the file in its own shape at the next generation). Nothing is lost from state, so the manifest block's downgrade posture is empty. This repository's own installed copy of the workflow changes only when it updates to 2.13.0. Orchestration Protocol 1.4 (unchanged). | [2.13.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.13.0) |
| 2.12.0 | 2026-10-15 | Review rounds converge. From round 2 a plan or implementation review (local and external stage) is given the changes since the last reviewed bundle and that round's findings, in a gitignored `CHANGES_SINCE_REVIEW.md` beside the bundle and in the archive; an approval still binds the full content. A verdict is checked for shape before it becomes state: a `REVISE` must name a Blocking or Important finding, an `APPROVE` may not list a Blocking finding or declare `Review scope: changes`, and a malformed verdict is refused and reissued, never converted. Orchestration Protocol 1.4 adds the `review_round` field to the `next-action` snapshot (derived from existing state; accepting at a cap stays a person's step) and states when a distinct-provider verdict courier at an `external_gate` is admissible (documentation only). `/milestone-plan` and `/apply-plan-review` ask for small plans and warn, without blocking, above 6 checkpoints. Closes workflow#28. Workflow 2.12.0 writes no new key or value to `WORKFLOW_STATE.json` or `WORKFLOW_CONFIG.json` and no new commit shape. It adds one gitignored file, `.ai-review/<id>/CHANGES_SINCE_REVIEW.md`, outside `bundle_id` and `review_content_id`, and one optional verdict header line, `Review scope:`. Workflow 2.11.0 never reads either: after a move back it ignores the header line, does not regenerate or delete the file (delete it by hand so a reviewer does not read a stale copy), and verifies an archive that carries it. A move back loses the severity refusal and the `review_round` field (an orchestrator reading protocol 1.4 sees 1.3 again). `review_round.plan` is exact only for an item whose plan-review rounds all ran under 2.7.0 or later; a consumer that must enforce a hard cap on any other repository counts rounds itself. This repository's own installed copy of the workflow changes only when it updates to 2.12.0. Orchestration Protocol 1.4. | [2.12.0](https://github.com/RodrigoFAbreu/workflow/releases/tag/v2.12.0) |
