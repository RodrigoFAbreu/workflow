# Workflow Roadmap

> For: anyone following where the Workflow is going. Last checked with: Workflow 2.18.5.

The full text of earlier versions is in this file's git history; the last long version is [here](https://github.com/RodrigoFAbreu/workflow/blob/f00c1c3/docs/ROADMAP.md).

## How to read this roadmap

- **What's next** is one ordered table. Work top to bottom; the first row that is not done is the current one.
- **Done** is the short history, newest first. The per-release list is in [the release history](release-history.md).
- **Later (open items)** explains the larger ideas that are not scheduled, with the direction to take when they are.
- **Open defects** lists the known problems that are not fixed yet. A defect found while running the Workflow is filed as an issue here, analysed, and then placed in **What's next** (as the next item) or under **Open defects** (later, with the reason): the owner's rule of 2026-10-16.
- Status words: **Done** (shipped), **Current** (being worked on now), **Next** (the item to start when the one above it is done), **Later** (agreed, not scheduled), **Waiting on ...** (blocked on something outside this repository).

## Later (open items)

None of these is scheduled, and none unlocks the operating model.

**Review-data simplification.** Review facts are currently spread over state, ledgers, bundles and feedback files, and some are kept in step by hand. That raises the cost of every review round and makes long-running work items heavy. Direction: continue what 2.5.0 began. Keep the current review state separate from immutable history, keep one authoritative copy of each fact and generate the other views from it, index history better, and compact long-lived work-item state. Add a persistent review file only when a concrete need cannot be met by state, ledgers, bundles, Git or a generated view. First slice, when scheduled: measure before changing anything. A script that reports, per work item, the size of its state entry, bundles and feedback and the number of facts stated in more than one place; a `docs:` or `test:` change with no release. Trigger: the Controller's review-load figures (a milestone with three plan reviews and five implementation revisions) or a state file whose size slows a command. Each later slice (one fact, one generated view) is its own `fix:` or `feat:`.

**Multi-worktree maturity.** Rows 25 and 26 are the first two slices (write the invariants down; test each one mechanically). What remains after them is the documented residual that mixed-release worktrees are unsupported: closing it needs the table to say which state a worktree on an older release may read, so it follows row 26.

**Longer-term evolution.** None is scheduled; each is one item with its own trigger, and a real operating problem picks it:

- Stronger transactional publication, and generalized repository-wide lifecycle leases: the continuation of rows 25 and 26, when the table shows a gap that a test cannot close.
- Cheaper review convergence and review-history compaction: the continuation of review-data simplification, once its measuring slice has numbers.
- A deprecation policy for very old governing versions, then tooling to retire historical compatibility branches: small and in order, a policy document first. Trigger: the last repository leaves "2.1" (none has a live item on it today).
- Compatibility contracts for the Controller and Workflow Manager integrations: the `manager` block is the Manager's contract already; the Controller's would be a document of what it reads from the protocol and when it may rely on it. Trigger: the next time a Controller release breaks on a Workflow or harness change (the Claude 2.1.304 refusal is the example).

**Functional validation evolution.** Where manual testing is weak or repetitive, strong automated evidence should be able to replace it: for the Workflow and the Manager, disposable-repository scenarios, migration, conformance and lifecycle end-to-end suites; for RepFlow, Room migration, Compose/UI, emulator end-to-end, backup/restore and navigation tests. Repository policy may still require a person's product or visual acceptance. The principle: stop for a person only when policy says the available evidence is not enough for the next decision. 2.8.0 delivered the mechanism; what remains is choosing and configuring evidence per repository.

## Principles

1. **Published releases are immutable.** Fixes ship as new releases.
2. **Work-item governance is durable.** Installing a newer Workflow never silently changes how an already-governed work item behaves.
3. **Review identity must describe exactly what was reviewed.** Approvals, bundles, ledgers and protected-path declarations stay consistent.
4. **Publish only durable truths.** Never claim a review-ready or approved state before its artifacts are valid and durable.
5. **Fail closed, recover cleanly.** Unknown or stale input stops progress with an actionable recovery instead of corrupting state.
6. **Repository-wide claims need repository-wide primitives.** A worktree-local lock cannot guarantee a repository-wide property.
7. **Legacy compatibility is explicit.** A fix for new work items is not automatically a fix for already-approved ones.
8. **One home per fact.** Keep minimal canonical state and derive views on demand; do not add files that restate what state, ledgers, bundles or Git already record.
9. **Dogfood migrations first.** Try them on a disposable repository before touching a real long-lived one.
10. **Size an item by what its reviewers must prove, not by its diff.** A planned item is releasable alone, of low to medium complexity, and adds at most one new mechanism. An item that combines concurrency, a trust or security record, or a launch path, or that has needed a second review round for the same class of finding, is split before the next review, and each part gets its own row with a complexity label. Optional findings are recorded and triaged; they never start another round. (Owner, 2026-10-23: deliver often and fast.)
