## 1. Goal

Ship Workflow 2.17.0, a minor release (`feat:`: a new script, a new optional
configuration key, new behaviour behind it), in which a Workflow-managed repository can
declare that its roadmap is a **structured backlog file** and get three things from the
Workflow instead of hand-editing prose:

1. `/milestone-plan` with no argument takes the next item from the file (the lowest
   `order` among the ready items).
2. Acceptance (`/accept-milestone` and the acceptance stage of `/satisfy-gate`) sets
   the item `done` in the file and regenerates the roadmap page, inside the acceptance
   commit, and never hand-edits the generated page.
3. The Workflow ships the generator and a staleness check (`check`), so a consumer's
   CI can fail a stale page without its own tooling.

A repository that declares nothing behaves exactly as today. This repository keeps its
prose `docs/ROADMAP.md` and does **not** declare a backlog file in this milestone; the
feature is exercised in tests and fixtures.

Everything is one new standard-library script, `scripts/workflow_backlog.py` (CLI and
module), one optional key in `WORKFLOW_CONFIG.json`, and command text that calls the
script. No state key, phase, commit shape or protocol field changes.

### Hard requirements (invariants)

- **INV-1 Undeclared means unchanged, without exception.** With no valid `backlog` key
  (absent, or the config missing or not a JSON object, where `load_config` keeps its own
  behaviour), every command's behaviour, every file it writes, every message and every
  generated byte (the artifact declarations included) are today's. The script answers
  "undeclared" and writes nothing; each command's undeclared text is the existing text,
  untouched; no classification gate is removed or added for such a repository.
- **INV-2 Fail closed, one next step.** A declared repository whose declaration or file
  is wrong stops with a stable code, what is wrong (with a line number for the file) and
  exactly one next step. Nothing falls back to prose editing, and nothing is written: after
  a refusal the backlog file and the page are byte-for-byte what they were (a page that did
  not exist still does not).
- **INV-3 The generated page is never hand-edited by the Workflow.** It is only ever the
  output of a generator (the declared command or the built-in one), plus, for a declared
  generator, the Workflow's own stamp of that generator's marker line (D-Generate); never an
  edit of its content.
- **INV-4 The edit lands in the acceptance commit**, where the roadmap edit lands today.
  All refusals that can be known beforehand come before any write of the command,
  including the pull-request fact the `requires_pr_approved` query stores (a pre-flight).
  A refusal of `accept` itself, which runs after the state completion, leaves the backlog
  file and the page byte-for-byte as they were and has one named recovery (D-Accept).
- **INV-5 Standard library only, one file, no Workflow-module imports.** The script can
  be copied out of a repository (the downgrade path relies on it).
- **INV-6 One meaning.** Every file the parser accepts is also valid YAML with the same
  meaning under a real YAML parser: the parser refuses what is ambiguous rather than
  guessing (D-Format).

### Non-goals

A board adapter or any mirror of the file; changing this repository's own roadmap;
the Controller's migration (it adopts this contract, A2); a managed-CI step that runs
`check` for a consumer (OD-8); marking items `in-progress` from a command (OD-3);
#30 part 2, #31, #39, #45, #50, #52, #55, #56.

### What is a gate and what is an aid

- **Gates (a failure stops work):** the unit tests of the script, the disposable-
  repository tests, the command-text pins, the release tests and the documentation
  check, as each checkpoint lists; at run time, every refusal of D-Messages; and
  `check` in a consumer's CI once the consumer wires it.
- **Aids (never a stop):** `status` (reports, exits 0), the advisory line `next` prints
  when an `in-progress` item is blocked (D-Select), and an optional cross-check test that
  compares the parser with PyYAML and is skipped when PyYAML is not installed.

## 3. Design decisions

### D-Declare: where the declaration lives and what it says

One optional key in `docs/ai-workflow/WORKFLOW_CONFIG.json`:

```json
"backlog": {
  "file": "docs/backlog.yaml",
  "roadmap": "docs/ROADMAP.md",
  "generator": ["python3", "tools/roadmap.py"]
}
```

- `file` is required. `roadmap` is optional and defaults to `docs/ROADMAP.md`.
  `generator` is optional: a non-empty array of non-empty strings, an argument vector
  (never a shell string).
- Unknown keys inside `backlog` are refused. `backlog` that is not an object (including
  `null`) is refused.
- A path is repository-relative with `/` separators: no leading `/`, no backslash, no
  empty, `.` or `..` segment, no control character, not under `.git/` or `.ai-review/`,
  and **no component of it, the last included, is a symbolic link** (an existing component
  that `lstat` reports as a link is refused; components that do not exist yet are fine). So
  the declared path **is** the canonical path: the collision check of D-Classify, the
  classification, the writes of `accept` and `generate` and the staging of the completion
  commit all name the same file, and a link such as `docs/via -> ../scripts` can neither
  reach a protected path nor make Git refuse to stage ("beyond a symbolic link"). Every existing
  component must also match its directory entry's exact name (a listing of the parent
  directory compared with the declared spelling, next to the `lstat` check), so a declared
  `Scripts/backlog.yaml` cannot pass the textual collision check on a case-insensitive
  filesystem while the write lands in `scripts/`; a mismatch is `declaration_invalid`. `file` and
  `roadmap` must differ. The check runs every time the declaration is loaded, so before any
  write of every subcommand (`declaration_invalid`, naming the link component).
- **Missing key, missing config file, an unparsable config or a config that is not a JSON
  object all mean undeclared.** The script reads one key and judges nothing else about the
  file: a corrupt or missing config is `load_config`'s concern, and it keeps its existing
  behaviour (a silent fall-back to `default_config()` before activation, a hard stop
  `ConfigMissingAfterActivationError` after it, which every Workflow command raises before
  it reaches the backlog). The script is stdlib-only and cannot tell the two apart, and it
  need not: both leave the repository exactly as it is today.
- The key applies to every work item whatever its governing version. It is not read by
  `load_config`/`validate_config` (their blast radius is every command); only
  `workflow_backlog.py` reads and validates it, so a malformed key stops the backlog-aware
  steps and nothing else.

**Why a config key and not a fixed path.** A repository that happens to contain
`docs/backlog.yaml` must not silently change how its acceptance behaves; an explicit,
committed, reviewed declaration is the only trigger. The path stays configurable; the
artifact template classifies the default names (D-Classify).

### D-Format: a strict YAML subset with its own parser (recommended)

Python has no YAML parser in its standard library. Options: (a) a strict, documented
subset of YAML with a purpose-written parser; (b) JSON in a `.yaml` file; (c) a vendored
or required YAML library. Recommendation **(a)**. (c) breaks the stdlib-only rule of every
Workflow script. (b) is valid YAML but is not what a person edits (no comments, a
trailing-comma trap, unreadable diffs) and not what the Controller's design names; it
would also need a second, different accepted form to meet the design. (a) costs a parser
of roughly 250 lines and its tests, once, and gives a file people can read and review.
INV-6 keeps the cost of being wrong low: the subset is closed under "means the same in any
YAML parser".

**The accepted file, exactly** (every other input is refused with
`<file>:<line>: <what>`):

1. UTF-8 without a byte-order mark, LF line ends only (a carriage return is refused), at
   most 256 KiB and 2000 lines, no line over 1000 characters, and every character inside
   YAML's printable set minus the line-break look-alikes. Exactly: U+0020 to U+007E,
   U+00A0 to U+D7FF except U+2028 and U+2029, U+E000 to U+FFFD except U+FEFF, and U+10000
   to U+10FFFF, plus the LF that ends a line. Everything else is refused with its line: every
   Unicode `Cc` character (C0 controls, tab, DEL and the C1 controls, U+0085 NEL included),
   U+2028 LINE SEPARATOR and U+2029 PARAGRAPH SEPARATOR (YAML 1.1 reads them as line
   breaks), U+FEFF anywhere in the file, and the noncharacters U+FFFE and U+FFFF.
2. Blank lines and comment lines (first non-space character `#`) anywhere. A trailing
   comment is a space then `#` after a value (outside quotes).
3. No document markers (`---`, `...`), directives, anchors (`&`), aliases (`*`), tags
   (`!`), block scalars (`|`, `>`), flow mappings (`{`), merge keys, multi-line scalars,
   nested mappings, or any value that is `null`, `~` or empty (the one exception is
   `depends_on:` immediately followed by a block list, rule 7; a `depends_on:` with no
   block list after it is refused, because YAML reads it as `null`, not as `[]`). Anchors, aliases, tags and block-scalar indicators are refused
   **only as the first character of an unquoted value**, where YAML reads them as
   indicators; inside a plain or quoted string they are ordinary characters (`R&D` and
   `"a *b"` are accepted, and PyYAML reads them the same). A plain value cannot start with
   them in any case (rule 6 requires a letter).
4. The top level is a mapping with exactly two keys at column 0, in either order:
   `version: 1` and `items:`. Anything else is refused. `items:` is followed either by a
   block sequence or, on the same line, by `[]` (an empty backlog).
5. Each item starts with `  - ` (two spaces, a dash, a space) and its first `key: value`;
   its other keys are at four spaces. Keys are plain words from this closed list, each at
   most once: `id`, `title`, `status`, `order`, `depends_on`, `size`, `detail`, `release`.
   An unknown or repeated key is refused.
6. Scalars, in a string field: **double-quoted** (the only escapes are `\\` and `\"`),
   **single-quoted** (`''` is one quote) or **plain**. A plain string must start with a
   letter (so it can never be read as a number, date or float), must not be one of
   `true false null yes no on off y n` in any case, must not contain `: ` or ` #`, must not
   end in `:`, and must not contain `[`, `]`, `{`, `}` or `,`. Anything else is quoted. The
   integer fields `order`, `size` and `version` are plain decimal digits, no sign, no
   leading zero, at most six digits; a quoted number there is refused. So an `id` or a
  `release` that starts with a digit (`2.17.0`) is written in quotes, and `accept --release`
  always writes it in double quotes.
7. `depends_on` takes `[]`, a one-line flow list of scalars (`[a, b]`, items under the
   scalar rules, separated by commas), or an empty value followed by a block list of
   `      - scalar` lines at six spaces (at least one). `depends_on:` with nothing after it
   (the next line is another key, an item or the end of the file) is refused, as is a block
   list that is empty. Absent means no dependencies. A flow list with a
   trailing comma or an empty entry (`[a, ]`, `[a, , b]`, `[,]`) is refused, though
   YAML 1.2 accepts the first: the subset is deliberately narrower (INV-6 only requires
   that what is accepted means the same).
8. Whitespace is pinned, not normalized: after a key's `:` there is **exactly one space**
   before its value (`title:   abc` is refused, though a YAML parser reads `abc`); a value
   is followed by nothing, or by **exactly one space** then `#` (a trailing comment); no
   line ends in a space (a blank line is empty, `title: abc ` is refused, though a YAML
   parser reads `abc`); inside a flow list the entries are separated by a comma and
   **one space** (`[a, b]`), with no space after `[` or before `]` or `,`. Every refusal
   names its line. So the accepted text has one reading in every parser and the editor
   of D-Accept can leave every other byte alone.

**The schema** (applied after parsing; all violations of one pass are listed, at most 10
shown, each with its line):

- `version` is `1`.
- `id`: required, matches `^[a-z0-9][a-z0-9_-]{0,63}$` (the work-item id pattern, so an
  item id **is** its work item id), unique.
- `title`: required, 1 to 200 characters.
- `status`: required, one of `idea`, `next`, `in-progress`, `done`.
- `order`: required, integer 1 to 999999, **unique across all items** (done and idea
  included, so the order is a total order and the generated page is stable).
- `depends_on`: each entry is the `id` of another item (not its own), no duplicate, and
  the graph has no cycle (the message names one cycle).
- `size`: optional integer 1 to 99, the estimated checkpoint count (the Controller splits
  above about five; OD-9).
- `detail`: optional, a repository-relative path as in D-Declare **and** made only of
  `[A-Za-z0-9._/-]` (so the Markdown link of D-Generate needs no escaping and cannot break
  a table row) **and** under `docs/items/` (the Controller's `docs/items/<id>.md`; this is
  what keeps every detail page inside the classified prefix of D-Classify, so no declaration
  needs one entry per page); no component of it is a symbolic link (the rule of D-Declare), and the file must
  exist and be a regular file.
- `release`: optional, only on a `done` item, 1 to 40 characters from `[A-Za-z0-9._+-]`
  starting with an alphanumeric (OD-5).

The order of items in the file is free (the page sorts by `order`). Status does not have to
agree with dependencies beyond D-Select (a `done` item may depend on an item that is not
`done`; it is shown, not refused).

### D-Select: which item `/milestone-plan` takes

`python3 scripts/workflow_backlog.py next`:

1. If any item is `in-progress` and **ready** (every `depends_on` is `done`), the one with
   the lowest `order` is chosen. An `in-progress` item is a milestone already started (for
   example by the Controller, or by hand): planning resumes it, never skips it. Other
   ready `in-progress` items are listed as `also_in_progress`.
2. Otherwise the ready item with status `next` and the lowest `order`. A `next` item that
   is not ready is skipped, not a block: a later ready one is chosen.
3. Otherwise a refusal, `no_ready_item`, whose message says which of the two cases holds:
   no item is `next` or `in-progress`, or each such item is waiting (it lists, per item,
   the ids it waits for).
4. An `in-progress` item that is **not** ready is never chosen; the output carries a
   `warnings` line naming it and the unfinished ids (an aid).

**Precedence over the active work item.** The backlog's choice is what the no-argument
`/milestone-plan` uses, even when `active_work_item_id` names a different non-terminal work
item (for example a ready `in-progress` item set by the Controller outranks a `next` item
already in planning). The command does not hide the mismatch: when the two differ it
prints one advisory line naming both ids and the explicit form
(`/milestone-plan <active id>`) that continues the active one, then proceeds with the
backlog's choice (an aid, never a stop).

The output is one JSON object: `declared: true`, `file`, and `item` (`id`, `title`,
`status`, `order`, `depends_on`, `size`, `detail`), plus `also_in_progress` and `warnings`.
`/milestone-plan` uses `item.id` as the work item id and, when `item.detail` is present,
reads that page (the item's prose) as the milestone's description; when `detail` is absent it
uses the item's `title` alone and says so. If that id already has a terminal work item,
`route_work_item` refuses as it does for any reused id; the troubleshooting page says to
mark the item `done`.

### D-Start: the Workflow does not write `in-progress` (OD-3)

`/milestone-plan` never changes the file. Reasons: the selection above is idempotent
(re-running it picks the same item until acceptance marks it `done`, which is exactly the
resume behaviour of an existing work item); a status write during planning would leave
two modified files (the file and the page) outside every gate and outside every commit
the planning step makes; and the Controller, which owns a loop, can set the status itself
and `next` honours it (rule 1). A `start` subcommand is not shipped.

### D-Accept: acceptance sets `done` and regenerates

- **Pre-flight** `python3 scripts/workflow_backlog.py preflight-accept <work-item-id>`,
  run before the command writes anything. The state completion is **not** the first write
  of `/accept-milestone`: the `requires_pr_approved` pre-flight (step 2a) stores the
  `workflow_gh` fact it read, also when it then refuses. So the human path runs the
  backlog pre-flight next to the optional-finding dispositions pre-flight, which already
  "runs before any query or write": immediately after it and **before** the
  `requires_pr_approved` pre-flight. `/satisfy-gate acceptance` runs it before its first
  step, which stores the same fact. It checks: declaration valid, file valid, the id is an item, its status is `next`,
  `in-progress` or `done` (`idea` is refused: promote it first), a built-in-generated page
  is replaceable (D-Generate), a declared generator's `argv[0]` resolves, and **the declared
  `file` and `roadmap` are not protected by the work item's own artifact declaration**
  (D-Classify, `declaration_conflict`: the check reads `<id>-artifacts.json` when it exists,
  so it covers declarations generated before 2.17.0 and hand-edited ones). It writes
  nothing. Undeclared: `{"declared": false}`. `accept` repeats the conflict check as its
  first step, before it snapshots or writes anything.
- **Apply** `python3 scripts/workflow_backlog.py accept <work-item-id> [--release V]`, at
  the step that edits the roadmap today (step 3): sets `status: done` (and `release: V`
  when given) by editing only those lines of the file, keeping every comment and every
  other byte; regenerates the page (D-Generate); prints the changed paths as JSON. The
  command stages exactly those paths in the completion commit with step 5a's.
- Re-accepting a `done` item changes nothing but still regenerates (so a stale page is
  repaired). A remediation child (non-null `parent_work_item_id`) is exempt: the existing
  text already skips the roadmap step for it.
- **Atomic.** The new file text is built in memory and re-parsed; it must equal the old
  data with only `status` (and `release`) changed, else the script refuses and writes
  nothing. Writes are temp-file plus rename. Before it writes anything `accept` snapshots
  **both** the backlog file and the page (their bytes, or the page's absence). If the
  generator then fails (non-zero exit, the timeout, a changed backlog file, or a page that
  breaks the freshness contract of D-Generate) or any later
  step refuses, **both are restored** from the snapshot (a page that did not exist is
  removed), so a declared generator that wrote part of the page before failing leaves no
  modified page; the refusal is `generator_failed`.
- **Only `file` and `roadmap` are staged.** `accept` prints exactly those two paths (the
  ones it changed, as declared: D-Declare leaves no symbolic link in them, so each is the
  path Git sees) as JSON and the completion commit stages them with step 5a's. A declared
  generator that also writes other files is the repository's own business: the Workflow
  neither detects nor stages them, and the shipped document says so (the generator should
  write only the page).
- **Recovery after an `accept` refusal.** `accept` runs at step 3, after the state
  completion (`complete_work_item`, persisted by `state_transaction` at step 2a, or by
  `/satisfy-gate`'s step 3), so the work item is already `MILESTONE_COMPLETE` with no
  completion commit, and a re-run of the command is refused by step 0 (terminal item).
  The pre-flight cannot catch `generator_failed`, a re-parse mismatch, or an edit of the
  file or page between the pre-flight and step 3. The recovery is one named step, the same
  in both commands, in `docs/ai-workflow/BACKLOG_FILE.md` and in `docs/common-problems.md`
  ("Acceptance stopped at the backlog"): fix the cause (the generator, the file), run
  `python3 scripts/workflow_backlog.py accept <work-item-id>` by hand (it is idempotent and
  works on a terminal item: the script reads no Workflow state), then continue the
  command that was running, from the step after `accept`, with the printed paths staged by
  its completion commit:
  - **human path (`/accept-milestone`)**: continue at its step 4, then 5, 5a, 6 (the
    completion commit, trailer `Workflow-Work-Item: <id>`), 7 and 8;
  - **policy path (`/satisfy-gate acceptance`)**: continue at its step 4, which runs
    `/accept-milestone` steps 2b and 3 to 8: step 3 re-runs `accept`, an idempotent
    regeneration, and the completion commit carries `Workflow-Gate-Satisfied-By:
    policy:<first 12 characters of the policy digest>` as well as `Workflow-Work-Item: <id>`;
    then its step 5 (record the floor, in its own commit, if the observed setting is
    stricter than `gate_policy_floor`) and step 6 (report the milestone as accepted **by
    policy**). The human-path steps above are not a substitute: they produce a commit
    without the policy trailer and record no floor. Every refusal code `accept` can print names this
  recovery as its next step (D-Messages). The commands say the same: on an `accept`
  refusal report it with the recovery, do not re-run the command, and write nothing else.
- **Release (OD-5).** `release` is optional and the command passes `--release` only when
  the milestone itself names a release (the plan or the user). Acceptance in the common
  case precedes publication, so the field is usually added later by hand in the file
  followed by `generate`; the file is the source, so that is a normal edit, not a page edit.
- **The next action.** `/accept-milestone` step 7 runs `next` read-only. The declared
  branch still does what the undeclared step does: it sets `docs/ACTIVE_MILESTONE.md`'s
  "Next action" (here to the item `next` returned, by id and title, ready for
  `PLANNING`, or to "no item is ready: <reason>" when `next` refuses) and reports the same
  in step 8. That is a report, not a failure, and the declared and undeclared branches
  leave the same files modified.
- **A work item with no `WORKFLOW_STATE.json` entry** (an ordinary `"1"` item that never
  got one) still gets the backlog branch: step 2a skips its *state* blocks for such an item,
  but the backlog pre-flight and step 3's declared branch read no Workflow state, so the
  command runs the pre-flight at the head of step 2a for it too (before any write) and step 3
  runs `accept`. The key applies whatever the item's governing version (D-Declare).
- A work item whose id is not an item of a declared backlog is refused at pre-flight
  (`item_unknown`): add an entry with that id (status `in-progress`) and retry.

### D-Generate: a built-in generator and `check`, a declared one wins

Recommended and small. Precedence, stated once: **a declared `generator` command, when
present, produces the page for `generate` and for acceptance; the built-in generator is
used only when none is declared; the two are never combined.**

- Declared generator: run with the argument vector as given, `cwd` the repository root,
  no shell, a 120 s timeout, stdout and stderr captured and shown on failure, and the
  environment variable `WORKFLOW_BACKLOG_SHA256` set to the SHA-256 (lower-case hex) of the
  backlog file's bytes at that moment. **The freshness contract** (what the Workflow can
  verify without trusting the command). The generator writes the page with exactly one line
  `<!-- backlog-sha256: <that hex> -->`, anywhere in it. After the command the Workflow
  requires, in this order: exit 0; the backlog file's bytes unchanged; the roadmap path is a
  regular file (not a symbolic link, not absent); the page contains exactly one line of that
  generator form with the file's digest and **no line of the stamped form below** (so a
  generator that did nothing to a page the Workflow stamped earlier fails, and so does one
  that copied the old line forward). Anything else is `generator_failed` (the file and the
  page restored, D-Accept), naming which of the four failed. Then the Workflow **stamps**
  the page: it replaces that one line, in place and atomically (temp file plus rename), with
  `<!-- backlog-sha256: <file hex> page-sha256: <page hex> -->`, where `<page hex>` is the
  SHA-256 of the page's bytes with that one line (its LF included) removed. Lines are split on LF
  alone; a final line without an LF is a line; a line ending in CR LF is not of the generator
  form (it fails closed, `generator_failed`, and `check` reports it as an unstamped marker).
  The stamp keeps the original line's terminator (an LF, or none for a final line), and
  `<page hex>` is computed over the same bytes at stamping and in `check` (the page with that
  one line, its terminator included, removed). Every other byte
  of the page is the generator's. So `["python3", "-c", "pass"]` fails (no page, or an old
  stamped page), a generator that leaves a stale page fails, and the page the Workflow keeps
  always carries a digest of the rest of its own content. The Workflow still does not judge
  what the page says.
- Built-in generator: deterministic, LF, no timestamps. The page is

  ```
  # Roadmap

  <!-- Generated from <file> by scripts/workflow_backlog.py. Do not edit by hand: edit the backlog file and run `python3 scripts/workflow_backlog.py generate`. -->

  | Order | Item | Status | Size | Depends on |
  | --- | --- | --- | --- | --- |
  | 16 | [Title](relative/path/to/detail.md) `id` | Next | 4 | other-id, another-id |
  ```

  Rows are sorted by `order`. The item cell is the title (a link when `detail` is set, the
  path made relative to the page's directory; `detail`'s restricted character set means the
  link target needs no escaping) and the id in backticks; status is `Idea`,
  `Next`, `In progress`, `Done` or `Done (<release>)`; empty size and no dependencies are
  `-`. Markdown-significant characters in a title (`\ | [ ] < >` and the backtick) are
  escaped. Nothing else (no prose sections: those live in the items' pages).
- **A hand-written page is never overwritten silently.** The built-in generator replaces
  an existing page only if it contains a line beginning `<!-- Generated from `; otherwise
  `generate` and acceptance refuse with `roadmap_not_generated` and one next step:
  `python3 scripts/workflow_backlog.py generate --replace` once (the old page stays in Git
  history), commit it, retry. A page that does not exist is created.
- `check`: file valid and, with the built-in generator, the page byte-equals the generated
  text (exit 0), else `roadmap_stale` (exit 1: the first differing line number, and the
  fix `generate`). With a declared generator `check` runs **no user code** and verifies
  from the stamp: the roadmap path is a regular file and carries exactly one line of the
  stamped form, whose file digest equals the digest of the file as it is now **and** whose
  page digest equals the digest of the page with that line removed (exit 0), else
  `roadmap_stale` (exit 1, naming a missing page, a missing, repeated or unstamped marker, a
  file digest that no longer matches the file, or a page digest that no longer matches the
  page, meaning the page was edited after it was generated). Verified and unverified
  freshness never share a result: there is no "exit 0, freshness is the generator's own"
  outcome. What a hand edit of the page cannot do is pass: it changes the page digest, and
  recomputing the stamp by hand is writing the file's generator, not editing a page.
- A consumer's CI step is `python3 scripts/workflow_backlog.py check`. This release does
  not add it to the managed workflow (OD-8); `docs/ai-workflow/BACKLOG_FILE.md` gives the step.

### D-Messages: every refusal

Every other code that `accept` can print after the state completion (`backlog_invalid`
from a file edited since the pre-flight, `roadmap_not_generated`, `declaration_invalid`,
`declaration_conflict` (an artifact declaration edited since the pre-flight),
and the re-parse mismatch, which is `backlog_invalid`) keeps the table's next step, followed
by the same recovery: when it is printed by `accept`, the next-step line ends "then run
`python3 scripts/workflow_backlog.py accept <id>` and continue the acceptance at step 4".
Output on a refusal is to stderr, two lines: `error: <code>: <message>` then
`next step: <one step>`; exit 2. A usage error (bad subcommand or flag) is also exit 2.
`check` on a stale page is exit 1. Everything else is exit 0 (`status` always exits 0 and
reports). Success output is one JSON object on stdout.

| Code | When | The one next step |
|---|---|---|
| `declaration_invalid` | the `backlog` key breaks D-Declare (the message names the field) | correct the key as `docs/ai-workflow/BACKLOG_FILE.md` says, or remove it to leave the backlog |
| `backlog_missing` | the declared file does not exist | create the file (`docs/ai-workflow/BACKLOG_FILE.md` has a starter), or remove the key |
| `backlog_invalid` | grammar or schema (D-Format; line numbers; at most 10 shown) | fix those lines, then run `check` |
| `no_ready_item` | D-Select rule 3 | set an item to `next`, or finish what it waits for, then run `/milestone-plan` again |
| `item_unknown` | acceptance names an id that is not an item | add an item with that id and status `in-progress` (an item in flight from before 2.17.0 also needs the backlog paths classified: `docs/ai-workflow/BACKLOG_FILE.md`, "Items in flight at adoption") |
| `status_not_acceptable` | acceptance of an `idea` item | set the item to `next`, then accept |
| `roadmap_not_generated` | the page exists, is not generated, built-in generator | run `generate --replace` once, commit, retry |
| `generator_failed` | the declared command failed, timed out, changed the file, or left no regular page carrying exactly one current generator-form `backlog-sha256` line (a stamped or stale line does not count) | fix the generator (the file and the page are restored), run `python3 scripts/workflow_backlog.py accept <id>`, and continue the acceptance at step 4 (D-Accept) |
| `roadmap_stale` | `check`, exit 1 (built-in: bytes differ; declared generator: page missing, stamp missing, repeated or unstamped, file digest not the file's, or page digest not the page's) | run `generate` and commit the page |
| `declaration_conflict` | the declared `file` or `roadmap` is protected by the work item's artifact declaration (D-Classify), at either stage | move the path out of the protected area in the `backlog` key (`docs/backlog.yaml` and `docs/ROADMAP.md` are never protected), then retry |

### D-Classify: the artifact template classifies the declared backlog paths

The backlog file, the generated page and the item pages are classified in **both** halves of
`generate_artifacts_declarations`, because the two halves have different sources, and only for
a **valid declaration**, at the declared paths. A repository with no declaration gets exactly
today's bytes, and `docs/backlog.yaml` and `docs/items/` stay unclassified there (an
`UnclassifiedPathError` at both stages, as now): no path is exempted by name or by default
(INV-1). The check of 2.14.0 (`assert_plan_artifact_declaration_coverage`) reads only the
backtick paths of a plan's checkpoint `**Files:**` paragraphs, and a consumer's plan never
names its own backlog file, roadmap page or item pages there, so it cannot be relied on to
name them. The template does it:

- **Reading the declaration.** `generate_artifacts_declarations` gains an optional keyword
  `repo_root=None`. When it is given, the function calls
  `workflow_backlog.declared_paths(repo_root)`, which returns the declared `file` and
  `roadmap` (the defaults when `roadmap` is omitted) as a list and never raises: an
  undeclared repository, an unreadable config or an invalid declaration yields an empty list
  (the template then adds nothing; the backlog script itself refuses an invalid declaration,
  with its own code, the first time it is used). `workflow_state` may import
  `workflow_backlog`; INV-5 forbids only the reverse. The import is **lazy, inside the
  `repo_root` branch** (the `workflow_forge` precedent), so a caller that omits `repo_root`
  never imports it. An `ImportError` there is a refusal (`declaration_invalid`, naming the
  missing script), never an empty list: a repository that declared a backlog but lacks the
  script must not silently lose its classification. The fixed script lists of the scratch
  installs (`install_workflow_scripts` in `workflow_test_harness.py`, the lists in
  `workflow_fingerprint_generalization_test.py`, `SCRIPT_FILES` of the acceptance matrix) gain
  `workflow_backlog.py` where a test reaches the `repo_root` branch (CP2, CP3). `/milestone-plan` step 3 passes
  `repo_root` (CP3). Every existing caller omits it and gets today's bytes. With an empty
  list nothing below applies.
- **Collision policy: refuse, before any write** (`declaration_conflict`). A declared path
  must not be *protected* by the declaration being generated, at either stage: the stage's
  own protected paths and, at the implementation stage, the work item type's protected
  prefixes (`IMPLEMENTATION_STAGE_DELIVERABLE_PREFIXES`: for a `product` item `config/`, `app/`,
  `gradle/`, `docs/adr/`; for a `process` item `scripts/` and `.claude/commands/`; plus the
  type's exact-path deliverables), because the classifier checks protected
  entries first (`classify_path`, `classify_path_implementation_stage`) and an excluded entry
  cannot win against them: acceptance's own edit of the file would then change protected
  content after the state completion and leave `technical_approval` stale. The same rule
  covers the item-page prefix (`docs/items/`). The shared predicate
  `workflow_backlog.protected_conflicts(paths, declaration)` takes the declared `file`,
  `roadmap` and the representative page path `docs/items/x.md` and the `plan_stage` and
  `implementation_stage` halves of an artifact declaration, and returns the conflicting
  paths. It is called by `generate_artifacts_declarations` on the declaration it just built
  (raising `BacklogError("declaration_conflict", ...)` before the caller writes a file),
  and by `preflight-accept` and `accept` on the work item's **existing**
  `docs/ai-workflow/registry/<id>-artifacts.json` when that file exists (a declaration
  generated earlier, or edited by hand, is covered; a work item with none is not checked).
  The refusal's one next step moves the path out of the protected area. A path that is
  merely *absent* from a declaration is not a conflict: that is the unclassified case of the
  repair below.
- **Implementation stage.** The declared `file` and `roadmap`, and the prefix `docs/items/`,
  are added as excluded entries with `setdefault`, after the collision check passed. The
  `_WORKFLOW_MACHINERY_*` tuples are **not** touched.
- **Plan stage.** The half starts from the frozen `fingerprint.PLAN_STAGE_EXCLUDED_PATHS`/
  `_PREFIXES`, which this release does **not** widen (salvage audit `I7`, the rule the code
  already cites: widening it moves existing approvals' identity). Instead
  `generate_artifacts_declarations` adds `plan_stage_excluded_paths.setdefault(...)` for the
  declared `file` and `roadmap` and `plan_stage_excluded_prefixes.setdefault("docs/items/",
  ...)`, the way it already adds `.workflow-manager/` and the product build files, with a
  justification naming the backlog files as repository territory.
- **Item pages.** The schema requires every `detail` to be under `docs/items/` (D-Format), so
  the one classified prefix covers every page; there is no per-page entry.

A declaration generated by 2.17.0 for a declared repository therefore never leaves the backlog
file, the page or an item page unclassified at either stage, with default or non-default paths,
and never classifies them as both protected and edited by acceptance. The plan-stage projection
is recomputed through implementation and at acceptance (`implementing_entry_reachable`, the
registry coverage check), so a consumer's backlog edit made after planning (the Controller
setting `in-progress`, an added item, a new `detail` page, acceptance's own edit) does not fail
closed with a bare `UnclassifiedPathError`.

**Declarations already written are not changed**, which leaves a gap for an item in flight
whose `<id>-artifacts.json` was generated before 2.17.0, or before the repository declared its
backlog: the declared `file`, `roadmap` and `docs/items/` are unclassified at both stages for
that item, and acceptance's own edit of the file, or a user's edit while it is in flight (the
`item_unknown` next step asks for one), would raise `UnclassifiedPathError`.
`docs/ai-workflow/BACKLOG_FILE.md` has an "Items in flight at adoption" section that states
the repair: add the declared `file` and `roadmap` paths and `docs/items/` as **excluded**
entries to both `plan_stage` and `implementation_stage` of that item's
`docs/ai-workflow/registry/<id>-artifacts.json` (the 2.14.0 declaration repair that
`PLAN_DECLARATION_NEXT_STEP` describes), and the `item_unknown` next step points at it. The
edit changes the declaration's bytes, so it **stales the item's existing approvals**: the
section states this and links "Repairing an artifact declaration after an approval" in
`docs/ai-workflow/REVIEW_PROTOCOL.md`, whose procedure is the one to follow (before the plan
approval it costs nothing; after it, a new plan revision through the two-stage review and
`/approve-review plan`; after the technical approval, a `post-fix` round and
`/approve-review implementation`), and says never to widen an exclusion to hide a path. The
repair is a classification of declared backlog paths only; if the paths are protected (the
`declaration_conflict` case) the repair is to move the path, not to exclude it.

### D-Downgrade: what 2.16.0 does with a repository that declared a backlog

2.16.0 ignores the `backlog` key (`load_config` never reads it), so a work item behaves as
before: `/milestone-plan` reads the generated page as if it were prose (a readable table,
no selection rule) and acceptance **hand-edits the generated page** (when `roadmap` is the default
`docs/ROADMAP.md`, the page 2.16.0's step 3 edits), after which the
staleness check fails in that repository's CI (built-in generator: the bytes differ;
declared generator: the stamp's page digest no longer matches the edited page), and the backlog file still says `next`.
With a non-default `roadmap` nothing fails: 2.16.0 edits or creates `docs/ROADMAP.md`, the
generated page is untouched, `check` still passes while the backlog says `next`, and the
backlog silently stops advancing.
Nothing in `WORKFLOW_STATE.json`, the ledgers or the commit shapes changes in either
direction, and 2.17.0 reads everything 2.16.0 writes. The census of `scripts/` gains one
file (`state_writer: false`); the update fixture of CP5 proves an in-flight item survives
it. **Moving back**: before updating to 2.16.0 finish or accept the items in flight under
2.17.0; after moving back either (1) keep the backlog: copy
`scripts/workflow_backlog.py` out first, to `tools/workflow_backlog.py` (or any path outside
`scripts/`, `.claude/`, `docs/ai-workflow/` and `.workflow-manager/`, which the 2.16.0 update
removes or manages; it imports nothing else), set the status in the file by hand and run the
copy's `generate` yourself at each acceptance (with a declared generator too: `generate`
runs it and stamps the page, so never run the generator directly, which leaves the marker
unstamped and fails `check`), and point the CI step at the copy,
`python3 tools/workflow_backlog.py check`; or (2) leave the backlog: delete the `backlog` key,
delete the CI check, and treat `docs/ROADMAP.md` as an ordinary hand-maintained page again
(it is a plain Markdown table). The manifest's `manager` block carries this posture;
`min_manager_version` stays `1.13.0`, since the Manager installs files from the manifest
without knowing their purpose.

## 7. Risks

- **A subset parser is a parser.** A bug accepts or refuses the wrong file. Mitigation: the
  grammar is closed and small, every rule has its own refusal test with a line number, the
  editor proves its own output by re-parsing, and the optional PyYAML cross-check runs on
  developers' machines that have it.
- **A declared generator is repository code run by an acceptance.** It is the repository's
  own committed command, run without a shell, with a timeout and without the Workflow
  trusting its output; the same trust CI already gives it. Documented.
- **An in-flight item at adoption** has no backlog entry and is refused at acceptance
  (`item_unknown`). Mitigation: the refusal's one next step, and the shipped document's
  "Items in flight at adoption" note (add the entry as `in-progress`, and, for an item
  whose declarations were generated before 2.17.0, classify the declared backlog paths and `docs/items/` in its
  `<id>-artifacts.json`, D-Classify).
- **Acceptance stops after the state completion.** `accept` can still refuse (generator,
  an edit since the pre-flight). Mitigation: both files restored, one named recovery
  (D-Accept), an acceptance-matrix scenario and a `common-problems.md` entry.
- **A declared generator that lies about freshness.** The Workflow verifies that the page is a
  regular file carrying the current file's digest, and stamps a digest of the rest, so a hand edit
  of the page is caught by `check` and by re-acceptance; it does not judge what the generator
  wrote, and a generator can emit the line without regenerating the content. Mitigation: the
  contract rules out the silent cases (no page, an old or stamped page, a hand edit, a generator
  that does nothing), the digest is the Workflow's to pass, and the generator is the
  repository's own committed code (the same trust as above).
- **A symbolic link in a declared path.** Refused at load (D-Declare), so collision checks,
  classification, writes and staging name one path.
- **A declared path inside a protected area.** Refused up front (`declaration_conflict`) at
  declaration generation and again at the pre-flight, so acceptance never edits protected
  content after the state completion.
- **Hand-written page replaced by mistake.** Refused unless marked generated or
  `--replace` is given; the replaced page is in Git history.
- **Two edits of one file.** A person editing the backlog while an acceptance runs; the
  acceptance rewrites only its own lines and refuses if the re-parse differs.
- **This repository runs 2.16.0.** The feature is exercised only in tests and fixtures;
  nothing here is declared.
